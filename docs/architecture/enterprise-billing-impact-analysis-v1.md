## 0. Architectural Conflicts Requiring Approval

Before any phase begins, stakeholders must resolve the following. **Implementation is blocked until these are decided.**

### CONFLICT A — Company Portal route

| Source | Proposed route |
|--------|----------------|
| Parent architecture v4 | `/dashboard/subscriptions/my` |
| Prior portal proposal v1 | `/dashboard/my-subscription` |
| **This specification** | `/dashboard/workspace/billing` |

**Recommendation:** Adopt **`/dashboard/workspace/billing`** as specified. Introduce a **`workspace` dashboard section** as the Company Admin operational hub (billing first; future workspace settings can nest alongside). Platform billing remains at **`/dashboard/subscriptions/*`**.

**Migration path:** No redirect required initially (greenfield route). Document canonical URLs in Route Registry.

---

### CONFLICT B — Platform Phase 2 routes vs BLOCKED_BILLING_PATHS

`billing-route-registry.ts` currently **blocks** `/payments`, `/invoices`, `/reports`, `/companies`, `/plans`, `/list` and redirects to overview.

The Platform Billing Center specification **requires** these sections. Unblocking is mandatory in Phase B — not a new parallel route tree.

**Recommendation:** Replace `BLOCKED_BILLING_PATHS` redirects with real registry entries phased across B–G. Keep `BILLING_BASE_NESTED_PATH = "/subscriptions"`.

---

### CONFLICT C — CRM Invoices vs Billing Invoices naming

| Route | Module | Table |
|-------|--------|-------|
| `/dashboard/invoices` | CRM customer invoices | `invoices` |
| `/dashboard/subscriptions/invoices` | Platform SaaS billing | `billing_invoices` |

**Recommendation:** Keep both. Use i18n disambiguation (`billing.nav.invoices` = "Billing Invoices"). No schema merge (per v4 contract).

---

### CONFLICT D — Payment Domain runtime location

Billing RPCs must not import Stripe/Paymob. Two valid patterns:

| Option | Pros | Cons |
|--------|------|------|
| **D1: Supabase Edge Functions** as Payment Service | Clean domain boundary, webhook isolation | New deployment surface |
| **D2: Postgres RPC + `payment_provider_adapters` table-driven** | Single stack | Provider SDK logic awkward in SQL |

**Recommendation:** **D1 — Edge Functions** as the Payment Service layer. Postgres owns state (`payment_intents`, `billing_payments`); Edge Functions own provider I/O. RPCs call Edge Functions via `pg_net` or return checkout URL generated by Edge Function invoked from RPC wrapper.

**Approval required** before Phase D.

---

### CONFLICT E — Migration numbering vs architecture v4 plan

Architecture v4 planned `045_billing_health.sql`, `046_billing_outbound_webhooks.sql`.  
**Shipped:** `045_billing_phase_a_rpcs.sql`, `046_billing_phase_a_completion.sql`.

**Recommendation:** Continue numbering from **047**. Do not renumber shipped migrations. Update architecture doc migration table separately (documentation debt, not blocking).

*Future — registry entry only until Phase G.

### 1.7 Post-payment workflow (canonical)

Single transactional RPC `billing.confirm_payment(p_intent_id)`:

1. Validate intent ownership via `current_company_id()`
2. Idempotency check (`provider_payment_id`)
3. Insert `billing_payments`
4. Insert `billing_invoices` (paid)
5. Insert `billing_receipts`
6. Renew `company_subscriptions` + `sync_company_subscription_denormalized`
7. Refresh entitlements snapshot
8. Refresh usage limit cache
9. Reactivate `profiles` where `account_status = 'SUSPENDED_BY_SUBSCRIPTION'`
10. Invalidate React Query keys (client) + optional server cache table
11. Insert in-app notifications
12. Enqueue `billing_email_outbox` rows
13. Write audit events (8+ event types)
14. Emit subscription events for timeline

Platform manual payment continues using `renew_subscription_from_payment` — converges on shared internal function `billing._apply_payment_success(...)`.

## 4. Security Impact Analysis

### 4.1 Threat model

| Threat | Mitigation |
|--------|------------|
| Cross-tenant data access | All portal RPCs use `current_company_id()`; reject client-supplied `company_id` |
| Privilege escalation (employee → admin actions) | Separate permissions: `billing.view_own` vs `billing.manage_own` |
| Payment intent hijacking | Intent rows scoped to company; confirm RPC verifies ownership + status machine |
| Webhook spoofing | Signature verification in Payment Service; idempotency keys |
| Audit tampering | RLS blocks client writes to `billing_audit_logs` |
| Coupon abuse | Rate limit + single-use/redemption caps in `billing_coupon_redemptions` |
| Refund fraud | Platform-only `refund_billing_payment`; requires `billing.edit` + audit |

### 4.2 RBAC additions

| Permission | Platform | Company Admin | Employee |
|------------|----------|---------------|----------|
| `billing.view` | ✅ | ❌ | ❌ |
| `billing.view_own` | Optional | ✅ | Optional read-only |
| `billing.manage_own` | ❌ | ✅ | ❌ |
| `billing.contact.edit_own` | ❌ | ✅ | ❌ |
| `billing.payment_method.manage_own` | ❌ | ✅ | ❌ |
| `billing.documents.download_own` | ❌ | ✅ | Optional |
| `billing.view_reports` | ✅ | ❌ | ❌ |
| `billing.edit` | ✅ | ❌ | ❌ |
| `billing.record_payment` | ✅ | ❌ | ❌ |
| `billing.refund` (new) | ✅ | ❌ | ❌ |

**Fix required:** Align `can_view_own_billing()` with `is_company_admin()` + `billing.view_own` (known Phase A gap).

### 4.3 RLS impact

| Table | Change |
|-------|--------|
| `billing_email_outbox` | Company read own; insert RPC-only |
| `billing_coupon_redemptions` | Company read own |
| `billing_revenue_snapshots` | Platform operator read only |
| `billing_refunds` | Platform operator read; RPC-only write |
| `profiles` | Reactivation via internal RPC only (no client UPDATE on `account_status`) |

Existing RLS on financial tables **unchanged** — still RPC-only writes.

### 4.4 Security regression checklist

- [ ] No new direct table INSERT/UPDATE from client for billing entities
- [ ] Every new RPC checks `auth.role() = 'authenticated'`
- [ ] Export RPCs enforce permission flags (`p_for_export` pattern)
- [ ] Payment confirm is idempotent
- [ ] Portal routes gated in registry + page + RPC (defense in depth)

## 5. Performance Impact Analysis

### 5.1 Hot paths

| Operation | Target | Strategy |
|-----------|--------|----------|
| Portal landing | < 300ms RPC | `get_workspace_billing_summary` single call |
| Platform overview | < 500ms | Existing paged RPC + cached revenue snapshot |
| Document center search | < 400ms | Paginated RPC with indexes on `(company_id, created_at desc)` |
| Revenue dashboard | < 1s | Pre-computed `billing_revenue_snapshots` (daily job) |
| Renewal pricing preview | < 200ms | Pure computation RPC, no external calls |
| Checkout initiate | < 2s | Includes Edge Function cold start; show loading state |

### 5.2 Index additions (recommended)

```sql
-- Platform cross-tenant lists
CREATE INDEX idx_billing_payments_status_created ON billing_payments(status, created_at DESC);
CREATE INDEX idx_billing_invoices_status_issued ON billing_invoices(status, issued_at DESC);
CREATE INDEX idx_company_subscriptions_renewal ON company_subscriptions(next_renewal_at) WHERE status IN ('active','trialing');

-- Portal documents
CREATE INDEX idx_billing_invoices_company_created ON billing_invoices(company_id, created_at DESC);

-- Outbox worker
CREATE INDEX idx_billing_email_outbox_pending ON billing_email_outbox(status, created_at) WHERE status = 'pending';
```

### 5.3 Caching strategy

| Cache | Location | Invalidation |
|-------|----------|--------------|
| React Query | Client | Mutation success + key invalidation |
| Entitlements | Optional server TTL table (Phase F) | Plan change, renewal, override |
| Revenue snapshots | Postgres daily | Nightly job |
| Usage snapshots | Existing `company_usage_snapshots` | Rollup job |

### 5.4 Scale considerations

| Volume | Approach |
|--------|----------|
| 10K companies | Paged RPCs sufficient |
| 100K+ usage records/month | Partition `usage_records` by month (Phase G) |
